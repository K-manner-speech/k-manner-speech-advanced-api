# Git 커밋 컨벤션

이 문서는 팀원이 GitHub에서 일관된 방식으로 브랜치를 관리하고 커밋과 Pull Request를 작성하기 위한 가이드입니다.

## 1. 기본 원칙

- `main`, `develop` 브랜치에는 직접 커밋하거나 Push하지 않습니다.
- 모든 변경은 목적에 맞는 작업 브랜치에서 진행하고 Pull Request를 통해 병합합니다.
- 하나의 커밋에는 하나의 논리적인 변경만 포함합니다.
- 커밋하기 전에 빌드, 테스트, 린트 등 프로젝트의 검증 절차를 수행합니다.
- 비밀번호, API 키, 인증서, 개인정보 등 민감한 정보는 커밋하지 않습니다.
- 의미 없는 커밋 메시지(`수정`, `작업`, `test`, `WIP` 등)는 사용하지 않습니다.

## 2. Gitflow 브랜치 전략

| 브랜치 | 용도 | 생성 기준 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 배포 가능한 운영 버전 | 상시 유지 | - |
| `develop` | 다음 배포를 위한 통합 개발 | `main`에서 최초 생성 | - |
| `feature/*` | 기능 개발 및 일반 작업 | `develop` | `develop` |
| `release/*` | 배포 준비, 버그 수정, 버전 정리 | `develop` | `main`, `develop` |
| `hotfix/*` | 운영 환경의 긴급 수정 | `main` | `main`, `develop` |

### 브랜치 이름

브랜치 이름은 영문 소문자와 숫자를 사용하고, 여러 단어는 하이픈(`-`)으로 구분합니다. 이슈가 있다면 이슈 번호를 포함합니다.

```text
<브랜치-종류>/<이슈번호>-<간단한-설명>
```

예시:

```text
feature/123-add-login
feature/update-user-profile
release/1.2.0
hotfix/145-fix-token-expiration
```

### 작업 흐름

1. 기능 개발은 최신 `develop`에서 `feature/*` 브랜치를 생성합니다.
2. 작업 완료 후 `develop`을 대상으로 Pull Request를 생성합니다.
3. 배포 시점에는 `develop`에서 `release/*` 브랜치를 생성합니다.
4. 배포 준비가 끝나면 `release/*`를 `main`과 `develop`에 각각 병합하고, `main`에 버전 태그를 생성합니다.
5. 운영 장애의 긴급 수정은 `main`에서 `hotfix/*`를 생성한 뒤 `main`과 `develop`에 각각 병합합니다.

## 3. 커밋 메시지 형식

커밋 메시지는 Conventional Commits 형식을 따릅니다.

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `type`: 필수. 변경의 종류를 작성합니다.
- `scope`: 선택. 변경된 기능, 모듈, 화면 등의 범위를 작성합니다.
- `subject`: 필수. 변경 내용을 한 줄로 요약합니다.
- `body`: 선택. 변경 이유와 구현 내용을 상세히 설명합니다.
- `footer`: 선택. 관련 이슈, Breaking Change 등을 작성합니다.

### 커밋 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 또는 수정 |
| `style` | 코드 동작에 영향을 주지 않는 서식 변경 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `test` | 테스트 코드 추가 또는 수정 |
| `chore` | 빌드, 패키지, 설정 등 기타 작업 |
| `perf` | 성능 개선 |
| `ci` | CI/CD 설정 변경 |
| `build` | 빌드 시스템 또는 외부 의존성 변경 |
| `revert` | 이전 커밋 되돌리기 |

### 제목 작성 규칙

- 제목은 변경 내용을 명확하고 간결하게 작성합니다.
- 제목 끝에는 마침표를 붙이지 않습니다.
- 타입과 범위는 영문 소문자로 작성합니다.
- 명령형 또는 현재형 표현을 사용합니다.
- 제목은 가급적 50자 이내로 작성합니다.
- `type` 뒤에는 콜론과 공백을 반드시 입력합니다.

```text
feat(auth): 소셜 로그인 기능 추가
fix(player): 음성 재생 중 중복 요청 문제 수정
docs: 로컬 개발 환경 설정 방법 추가
refactor(api): 사용자 조회 로직 분리
```

잘못된 예시:

```text
기능 수정
feat: 로그인 추가함.
Fix : bug fix
WIP
```

### 본문과 푸터 작성 규칙

- 본문에는 무엇을 변경했는지뿐 아니라 필요한 경우 왜 변경했는지도 작성합니다.
- 제목과 본문 사이에는 빈 줄을 둡니다.
- 관련 이슈는 푸터에 `Closes #이슈번호`, `Fixes #이슈번호`, `Refs #이슈번호` 형식으로 작성합니다.
- 호환성을 깨뜨리는 변경은 제목의 타입 뒤에 `!`를 붙이고 푸터에 `BREAKING CHANGE:`를 작성합니다.

```text
feat(api)!: 사용자 응답 형식 변경

클라이언트에서 불필요한 중첩 객체를 제거할 수 있도록
사용자 응답 데이터 구조를 단순화한다.

BREAKING CHANGE: user 필드 내부의 profile 객체가 제거됨
Closes #123
```

## 4. 커밋 단위

- 기능 추가, 리팩터링, 문서 수정 등 서로 다른 목적의 변경은 별도 커밋으로 분리합니다.
- 각 커밋은 가능한 한 독립적으로 이해하고 되돌릴 수 있어야 합니다.
- 자동 포맷팅으로 인한 대규모 변경과 기능 변경은 같은 커밋에 포함하지 않습니다.
- 커밋 전 `git diff`와 `git status`로 포함될 파일을 확인합니다.
- 작업 중간 저장이 필요하면 로컬에서 임시 커밋을 사용할 수 있지만, Pull Request 전에는 의미 있는 단위로 정리합니다.

## 5. Pull Request 규칙

- Pull Request 제목도 커밋 메시지 형식을 따릅니다.
- 본문에는 작업 목적, 주요 변경 사항, 테스트 결과, 관련 이슈를 작성합니다.
- UI 변경이 있다면 스크린샷 또는 영상을 첨부합니다.
- Pull Request는 한 가지 목적에 집중하고, 리뷰 가능한 크기로 유지합니다.
- 최소 1명 이상의 승인을 받은 뒤 병합합니다.
- 리뷰 의견이 반영되고 필수 CI 검사가 통과한 뒤 병합합니다.
- 자신의 Pull Request를 임의로 승인하지 않습니다.
- 병합 후 사용이 끝난 작업 브랜치는 삭제합니다.

Pull Request 제목 예시:

```text
feat(auth): 카카오 로그인 기능 추가
fix(api): 사용자 조회 시 발생하는 예외 수정
```

## 6. 병합 및 버전 태그 규칙

- 팀에서 별도로 정하지 않았다면 작업 브랜치는 `Squash and merge`하여 불필요한 중간 커밋을 정리합니다.
- `release/*`, `hotfix/*` 브랜치는 이력을 보존할 수 있도록 일반 병합을 사용합니다.
- 공유 브랜치의 커밋 이력을 임의로 변경하는 강제 Push(`--force`)는 금지합니다.
- 배포 버전은 Semantic Versioning을 따르는 `v<major>.<minor>.<patch>` 형식으로 태그합니다.

```text
v1.0.0
v1.2.0
v1.2.1
```

- `major`: 호환되지 않는 변경
- `minor`: 하위 호환되는 기능 추가
- `patch`: 하위 호환되는 버그 수정

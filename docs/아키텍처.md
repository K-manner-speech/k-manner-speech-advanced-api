# K-Manner Speech 솔루션 아키텍처

> 상태: MVP 1.0 아키텍처 기준안  
> 기준일: 2026-08-24  
> 범위: 기술 결정, 계층·보안 경계, 로컬 스캐폴딩, NFR, API 계약  
> 제외: 기능 코드, DB 테이블/컬럼 설계, Alembic migration 구현, 실제 API·AI prompt 구현

## 1. 목적과 기준 문서

이 문서는 다음 문서를 제품·구조 기준으로 대조해 작성했다.

- `docs/PRD.md`
- `docs/화면기획서.md`
- `docs/DESIGN_SYSTEM.md`
- `docs/Coding_Convention.md`
- `docs/PROJECT_STRUCTURE_V5.md`

우선순위는 사용자가 이번 아키텍처 협의에서 명시적으로 확정한 결정, PRD, 화면기획서, 프로젝트 구조, 디자인 시스템, 코딩 컨벤션 순이다. 문서 간 충돌이나 새로운 미정이 발견되면 구현자가 추정하지 않고 ADR 후보로 올린다.

핵심 원칙은 다음과 같다.

1. **판정은 서버에서 한다.** 인증, 권한, 소유권, 허용된 페르소나-시나리오 조합, 대화 종료, 점수·피드백 상태, 자료 분석 가능 여부를 React가 최종 판정하지 않는다.
2. React는 화면 상태와 사용자 입력을 관리하고 FastAPI의 결과를 표현한다.
3. 사용자 소유 데이터는 `API -> Service -> Repository -> Supabase` 경계를 반드시 거친다.
4. AI 텍스트, TTS, 감정, 피드백은 독립 상태를 가지며 부분 실패가 전체 대화를 실패시키지 않는다.
5. 비밀값, 원문 AI payload, 문서 내용과 signed URL을 로그에 남기지 않는다.

## 2. 실행 범위와 시스템 컨텍스트

MVP는 배포하지 않고 로컬에서 개발·시연한다. React, FastAPI, Python worker는 호스트에서 실행하며 Supabase, Gemini API, OpenAI API만 원격 관리형 서비스를 사용한다. 클라우드 배포, 고가용성, 운영 autoscaling은 범위 밖이다.

```text
React/Vite
  |-- Supabase Auth 직접 호출: 가입·로그인·복구·비밀번호 변경
  |-- Authorization: Bearer <Supabase access token>
  v
FastAPI /api/v1
  |-- 인증·검증·소유권·제품 판정
  |-- SQLAlchemy/psycopg --> Supabase Postgres 비노출 app schema
  |-- UploadFile stream --> Supabase Storage private buckets
  |-- pgmq.send ----------> Supabase Queues
  v
Python worker
  |-- pgmq.read/set_vt/delete/archive direct SQL
  |-- Gemini: 채팅·rolling summary·TTS·감정
  |-- OpenAI: 피드백·면접 분석·embedding
  `-- 결과를 기존 domain/job record에 멱등 갱신
```

## 5. 계층과 판정 책임

```text
router(API) -> service -> repository -> SQLAlchemy/psycopg -> Supabase Postgres
                          \-> storage adapter -> Supabase Storage
service -> job publisher -> pgmq -> worker -> provider adapter
```

| 계층 | 책임 | 금지 |
| --- | --- | --- |
| Router/API | route, Bearer dependency, Pydantic validation, HTTP status, idempotency header 수집 | 소유권 판정, 직접 owner-data query, AI 호출 |
| Service | 제품 규칙과 최종 판정, 상태 전이, transaction orchestration, repository 조합 | request body의 user ID 신뢰, owner-data 직접 SQLAlchemy query |
| Repository | owner predicate가 포함된 read/write/delete, lock·atomic update, persistence query | HTTP status·UI 판단, owner ID 생략 |
| Supabase/Postgres | constraints, transaction, 최소 권한, non-exposed schema, pgmq/pgvector | 사용자 JWT 없는 runtime query에서 RLS가 owner 검사를 대신한다고 가정 |
| Worker | lease, deadline/retry, provider adapter, stale check, 멱등 결과 저장 | 사용자 입력만으로 owner 결정, raw payload logging |

**서버 판정 예시:** Front가 `completed`, 점수, persona-scenario 허용, file 분석 가능, owner ID를 보내더라도 신뢰하지 않는다. Service가 인증 subject와 저장 상태를 기준으로 판정하고 Repository에 인증 user ID를 필수 전달한다.

## 6. 인증과 접근 제어

### 6.1 인증 흐름

- 가입·로그인·password recovery/reset/change는 React가 Supabase Auth에 직접 호출한다. FastAPI는 비밀번호를 받지 않는다.
- MVP는 email/password만 지원한다. OAuth/account linking은 범위 밖이다.
- 로컬 MVP는 email verification을 끄고 가입 직후 온보딩한다. 운영 전환 전 반드시 켠다.
- Supabase session은 `sessionStorage`에만 보존한다. 같은 탭 refresh는 복원하고 탭/브라우저 종료, logout, account deletion에서 제거한다.
- React는 FastAPI에 `Authorization: Bearer <access token>`을 보낸다.
- 일반 API와 polling은 JWKS cache 기반 로컬 JWT 검증을 사용한다. 허용 `alg`, `iss`, `aud`, `exp`를 검증한다.
- `kid` miss/key rotation 시 JWKS를 refresh하고 한 번만 재검증한다.
- 회원 탈퇴 등 민감 작업은 Supabase Auth `get_user`로 재확인한다.
- 인증과 데이터 소유권 검사는 별개다.

### 6.2 DBA 구현 기준

1. 애플리케이션 테이블은 Supabase Data API에 노출되지 않는 전용 schema에 둔다. 실제 schema 이름은 migration에서 한 번 확정하고 PostgREST exposed schema 목록에 추가하지 않는다.
2. `anon`, `authenticated` 역할에는 이 schema의 `USAGE` 및 table CRUD, sequence, function execute 권한을 부여하지 않는다. 기존 implicit/default privilege도 검사해 회수한다.
3. Migration role과 runtime role을 분리한다.
   - `MIGRATION_DATABASE_URL`: schema owner, DDL, extension/GRANT/default privilege 관리.
   - `DATABASE_URL`: API+worker가 공유하는 runtime role. 필요한 DML, sequence usage, allowlisted function execute만 허용. DDL, role 변경, schema owner 권한 금지.
4. `pgmq`는 Data API/`pgmq_public`로 노출하지 않는다. Runtime role에는 승인된 queue의 `pgmq.send/read/delete/archive/set_vt` 등 필요한 함수만 signature 단위로 `EXECUTE`를 부여한다. Queue create/drop과 광역 schema 권한은 migration role만 가진다.
5. Storage service role key는 API/worker server environment에만 둔다. Browser에는 publishable/anon key만 제공한다.

### 6.3 행 소유권 강제

- 인증 dependency가 JWT `sub`를 canonical `authenticated_user_id`로 만든다. Body/query/path의 사용자 ID는 owner 판정에 사용하지 않는다.
- 모든 사용자 소유 Repository method는 `authenticated_user_id`를 필수 positional/keyword 인자로 받는다.
- Read는 resource ID와 `owner_id = authenticated_user_id`를 같은 query predicate에 넣는다.
- Update/delete는 먼저 다른 사람의 row를 읽지 않고 resource ID와 owner predicate를 같은 atomic statement에 넣고 affected row count를 검사한다.
- 관계형 child 접근은 parent ownership을 join/exists predicate로 같은 query 안에서 검증한다. 예: message/TTS/feedback는 연결 room의 owner를 확인한다.
- 존재하지 않음과 다른 사용자 소유는 모두 동일한 `404` code/message/timing class로 응답해 resource enumeration을 막는다.
- Service/Router의 owner-data 직접 SQLAlchemy query는 lint/review 금지 항목이다. 공개 catalog/health처럼 owner가 없는 단순 조회만 예외다.
- Job polling도 job owner predicate를 적용하고 `result_resource`는 owner 검증 후에만 제공한다.
- Signed URL 발급 전 DB metadata owner와 object key prefix를 모두 확인한다. URL은 짧게 만료되고 로그에 남기지 않는다.
- 현재 direct Postgres runtime session에 사용자 JWT를 주입하지 않으므로 RLS를 서버 owner 검사 백업으로 간주하지 않는다. 향후 명시적으로 Data API에 노출하는 객체만 RLS를 defense-in-depth로 활성화하고 ADR·권한 테스트를 거친다.

### 6.4 CORS·CSP·오류 노출

- `CORS_ALLOWED_ORIGINS`는 scheme+host+port 정확 allowlist이다. Wildcard와 광역 localhost regex를 금지한다.
- Method와 `Authorization`, `Content-Type`, `Idempotency-Key` 헤더만 실제 사용 범위로 허용한다.
- Dev CSP는 Vite HMR 최소 예외만, build/preview는 `default-src 'self'`와 승인된 FastAPI/Supabase 연결 및 필요한 image/media/style source만 허용한다. Inline script와 임의 origin을 금지한다.
- Supabase Auth 오류는 account enumeration을 피하는 안정적 client error code로 매핑해 i18n한다.

## 7. 데이터·파일 생명주기

- 사용자 자료와 TTS WAV는 Supabase Storage private bucket에 둔다. 공개 URL은 금지한다.
- 업로드는 FastAPI proxy 방식이다. `UploadFile` streaming, auth/owner, 확장자+magic bytes/actual MIME, 10MB 상한, server-generated object key를 적용한다.
- PDF/DOCX만 허용한다. DOCX macro·비정상 archive를 거부하고 파일을 실행하지 않으며 text extraction만 수행한다.
- ClamAV와 OCR은 MVP에 포함하지 않는다. Parsing time/memory/page limit을 적용하고 텍스트 추출 threshold 미달은 `DOCUMENT_TEXT_NOT_EXTRACTABLE`로 분석 queue 진입을 막는다.
- 저장 실패/metadata 확정 실패는 중간 object를 정리한다.
- 다운로드·재생은 owner 검증 후 짧은 signed URL로 제공한다.
- 자료 교체/삭제, room 삭제, account deletion은 PRD의 즉시 영구 삭제 범위를 따른다. Processing worker는 provider 호출 전과 저장 전에 resource owner/version을 다시 검사해 stale 결과를 버린다.
- Application-level field encryption은 MVP에 추가하지 않는다. Supabase at-rest encryption, non-exposed schema, least privilege, owner predicate를 사용하며 운영 위협 모델에서 재검토한다.

## 8. Queue와 Worker

### 8.1 Queue 분리와 처리

- `conversation_text`: 최우선. Gemini 대화 텍스트와 필요 시 rolling summary.
- 대화형 고우선순위 queue: TTS, 감정 분석, 발화 피드백.
- 문서분석 저우선순위 queue: 문서 추출 후 embedding/면접 자료 분석.
- Queue는 durable/basic pgmq를 사용하고 unlogged queue는 사용하지 않는다.
- FastAPI는 auth/validation/save/enqueue 후 `202 Accepted + job_id`를 반환한다.
- React는 `GET /api/v1/jobs/{job_id}`를 2초 간격으로 polling하고 succeeded/failed/제품 최대 대기시간 도달 시 중단한다.
- Gemini 대화 텍스트 성공 후 TTS·감정·피드백을 fan-out한다.

### 8.2 Job 계약

공통 상태는 `queued`, `processing`, `succeeded`, `failed`, `cancelled`다. Job API에는 `type/status/progress/error/result_resource`만 제공하고 domain 결과는 성공 후 별도 조회한다.

- 전송 오류 429/5xx/timeout: 총 3회(최초 1+재시도 2), exponential backoff+jitter.
- `Retry-After`는 기능 deadline 안에서만 우선한다.
- 기능 deadline은 PRD 기준: 대화 텍스트 15초, 감정 15초, 피드백 30초, TTS 45초, 자료 분석 60초. Deadline이 다음 retry보다 우선한다.
- Structured output Pydantic 검증 실패는 같은 job record에서 안전한 validation summary로 exactly one repair retry. 두 번째 실패는 final failed.
- Transport retry counter와 schema repair counter를 분리한다.
- Result write는 기존 단일 processing/domain record에 멱등 갱신한다.
- 사용자별 queued+processing 한도는 Postgres에서 atomic 판정한다. Provider별 worker concurrency는 환경변수이며 숫자는 부하 측정으로 정한다. 초과는 retryable `429`다.

### 8.3 Visibility·DLQ·취소

- Worker wrapper가 transaction과 visibility timeout을 명시한다. 처리 중 필요하면 `set_vt`로 lease를 연장하고 중복 consumer에서도 job 상태 compare-and-set으로 단일 효과를 보장한다.
- 최종 실패는 queue별 `<queue>_dlq`로 안전 메타데이터(job_id/type/attempts/safe error/timestamps)만 원자적·멱등 이동한 뒤 source에서 제거한다.
- DLQ list/replay는 local admin CLI만 제공한다. Replay 전 job/resource/owner/version/현재 eligibility를 검사하고 새 idempotency key로 enqueue하며 안전 audit metadata를 남긴다.
- 범용 사용자 cancel API/UI는 없다. Delete/replace/account deletion이 queued job을 cancel하며 stale worker 결과를 저장하지 않는다.

## 9. AI와 RAG

### 9.1 Provider 경계

Provider SDK는 `app/ai/interfaces.py` 뒤에 둔다. Service는 vendor response를 직접 해석하지 않고 adapter가 Pydantic domain result로 변환한다.

환경변수:

```text
GEMINI_CHAT_MODEL
GEMINI_TTS_MODEL
GEMINI_EMOTION_MODEL
OPENAI_FEEDBACK_MODEL
OPENAI_INTERVIEW_MODEL
OPENAI_EMBEDDING_MODEL=text-embedding-3-large
```

모든 model ID는 시작 시 누락·API 허용 여부를 검사한다. `.env.example`에는 문서 검증일과 공식 링크가 있는 예시만 넣고 secret을 넣지 않는다. Preview TTS model은 고정 상수로 숨기지 않는다.

Provider-side 저장은 지원되는 옵션에서 끈다(OpenAI `store=false`). No-training/장기 보존 비활성 계정 설정을 startup checklist로 확인한다. 로컬에는 정규화된 메시지·피드백·source refs만 저장하고 raw request/response/reasoning/trace를 보존하지 않는다. 진단은 model, provider request ID, usage, safe error code만 남긴다.

### 9.2 대화 context

- 최근 메시지는 원문으로 유지한다.
- 측정된 token budget 이전에 오래된 span을 Gemini rolling structured summary로 만든다.
- Schema는 relation, situation, goals, agreements, unresolved, explicit important facts를 포함하고 inferred facts를 금지한다.
- Summary version과 last included message ID를 저장한다.
- 다음 입력은 summary+recent raw이며 trigger threshold는 공식 context limit과 대표 대화 측정으로 정한다.

### 9.3 RAG

```text
검증된 text PDF/DOCX
 -> local text extraction/normalization
 -> section-first chunks (initial configurable 500 tokens, 75 overlap)
 -> text-embedding-3-large
 -> pgvector + owner/document/version/source metadata
 -> owner/version metadata prefilter
 -> cosine/vector similarity top_k=5
 -> evaluation-derived threshold
 -> only passing evidence to GPT-5.6 Luna
 -> structured output + source refs
```

- Section/page/paragraph source refs를 보존한다.
- Threshold 숫자를 임의 설정하지 않고 대표 한국어 이력서 retrieval evaluation으로 도출한다.
- 통과 chunk가 없으면 `insufficient_evidence`; 자료에 없는 사실을 만들지 않는다.
- Exact keyword miss가 반복될 때만 hybrid FTS를 재검토한다.
- 원본 교체는 새 document version을 re-embed하고 이전 활성 version을 배제한다. 삭제는 관련 chunks/vectors를 cascade 제거한다.

## 11. API 공통 계약

### 11.1 공통

- Base prefix: `/api/v1`
- JSON은 UTF-8. Upload만 multipart.
- 재시도 가능한 create/action API는 React가 생성한 UUID `Idempotency-Key` header가 필수다.
- Scope는 `user_id + route/action + key`; request fingerprint와 result를 저장한다.
- 같은 key+같은 payload는 기존 resource/job을 반환하고, 같은 key+다른 payload는 `409`다.
- 목록은 `(created_at,id)` stable order의 opaque cursor를 사용한다: `limit`, `next_cursor`. Resource별 asc/desc를 명시한다.

오류 envelope:

```json
{
  "error": {
    "code": "STABLE_MACHINE_CODE",
    "message": "safe default/developer message",
    "field_errors": [{"field": "name", "code": "INVALID_VALUE"}],
    "request_id": "uuid",
    "retryable": false
  }
}
```

FastAPI 전역 handler가 Pydantic validation, auth, domain, provider/queue 오류를 이 형식으로 통일한다. Client는 `code`를 i18n한다.

### 11.2 상태 코드 기준

| 코드 | 용도 |
| --- | --- |
| 200 | 조회·수정·기존 멱등 결과 |
| 201 | 동기 resource 생성 |
| 202 | 비동기 job 수락 |
| 204 | 응답 body 없는 삭제/로그아웃 후 정리 |
| 400 | 형식 외 잘못된 요청 |
| 401 | token 없음/만료/invalid |
| 403 | 인증됐으나 제품 상태상 금지; owner mismatch에는 사용하지 않음 |
| 404 | resource 없음 또는 다른 사용자 소유 |
| 409 | 상태 충돌, invalid persona-scenario, idempotency fingerprint 충돌 |
| 413 | 10MB 초과 |
| 415 | 지원하지 않는/MIME 불일치 파일 |
| 422 | field validation/document parsing 조건 실패 |
| 429 | user backpressure/provider 제한, retryable |
| 500 | 안전하게 변환된 내부 오류 |
| 503 | DB/queue readiness 실패 또는 일시 불가 |

DTO의 구체 필드명은 Pydantic/OpenAPI가 최종 기준이다. 아래는 구현 전에 지켜야 할 route·입출력·상태 계약이며 DB schema를 의미하지 않는다.

## 13. NFR와 품질 게이트

### 13.1 시간·복원력

- PRD deadline: text 15s, emotion 15s, feedback 30s, TTS 45s, document analysis 60s.
- Text 성공은 즉시 저장·표시하고 downstream 상태를 독립 저장한다.
- Retry는 같은 record를 갱신하고 중복 결과를 만들지 않는다.
- Offline/timeout/partial/empty/error는 현재 상태와 retry/fallback을 제공한다.

### 13.2 접근성·반응형

- WCAG 2.2 AA 목표, keyboard operation, visible focus, 4.5:1 text contrast, 3:1 large text/graphics, 44x44 touch, 200% zoom.
- 감정·점수·상태는 색만으로 전달하지 않는다. Audio에는 text, persona image에는 role/emotion alt를 제공한다.
- Reduced motion을 존중한다. Storybook a11y, RTL interaction, Playwright core E2E로 검증한다.

### 13.3 로깅·관측성

- JSON log 필드: request_id/job_id, safe internal user_id, route/job type, status, duration, provider error code.
- 금지: token, API key, raw prompt/response, reasoning/trace, user document, signed URL.
- `/health/live`, `/health/ready`를 분리한다. Ready는 짧은 timeout으로 DB, required extension/queue/config, worker heartbeat를 확인하고 AI provider를 실제 호출하지 않는다.

## 17. 아키텍처 완료 기준

- 모든 stack 항목에 채택 이유가 있다.
- Router/API, Service, Repository, Supabase 책임과 import/query 금지가 구분된다.
- 인증 subject와 owner predicate가 분리되고 모든 소유 resource에 같은 query-level owner 검사가 적용된다.
- `anon/authenticated`, migration role, runtime role, Storage service role의 권한 경계가 구현 가능하게 명시된다.
- Queue, retry, deadline, polling, DLQ, stale-result 처리와 부분 성공이 PRD 시간 기준과 일치한다.
- API path, request/response 책임, 주요 status code, error envelope, idempotency, cursor 계약이 정의된다.
- 기능 코드·DB schema·API 구현은 포함하지 않는다.

# K-Manner Speech 솔루션 아키텍처

> 상태: v1.1.0 개발 아키텍처 기준안
> 기준일: 2026-09-03
> 범위: 기술 결정, 계층·보안 경계, 로컬 스캐폴딩, NFR, API 계약  
> 제외: 기능 코드, DB 테이블/컬럼 설계, DB migration 구현, 실제 API·AI prompt 구현

## 1. 목적과 기준 문서

이 문서는 다음 문서를 제품·구조 기준으로 대조해 작성했다.

- `docs/PRD.md`
- `docs/화면기획서.md`
- `docs/DESIGN_SYSTEM.md`
- `docs/Coding_Convention.md`
- `docs/PROJECT_STRUCTURE_V5.md`

우선순위는 사용자가 이번 아키텍처 협의에서 명시적으로 확정한 결정, PRD, 화면기획서, 프로젝트 구조, 디자인 시스템, 코딩 컨벤션 순이다. 문서 간 충돌이나 새로운 미정이 발견되면 구현자가 추정하지 않고 ADR 후보로 올린다.

핵심 원칙은 다음과 같다.

1. **판정은 서버에서 한다.** 인증, 권한, 소유권, 허용된 페르소나-시나리오 조합, 대화방 상태·종료 가능 유형·종료 원인·평가 범위, 점수·피드백 상태, 자료 분석 가능 여부를 React가 최종 판정하지 않는다.
2. React는 화면 상태와 사용자 입력을 관리하고 FastAPI의 결과를 표현한다.
3. 사용자 소유 데이터는 `API -> Service -> Repository -> Supabase` 경계를 반드시 거친다.
4. AI 텍스트, TTS, 감정, 피드백은 독립 상태를 가지며 부분 실패가 전체 대화를 실패시키지 않는다.
5. 비밀값, 원문 AI payload, 문서 내용과 signed URL을 로그에 남기지 않는다.
6. 대화방의 `completed`는 종료 여부를, 기존 필드인 `ended_reason`은 종료 원인을 나타낸다. 둘을 하나의 상태값으로 혼합하지 않는다.

## 2. 실행 범위와 시스템 컨텍스트

MVP는 배포하지 않고 로컬에서 개발·시연한다. React, FastAPI, Python worker는 호스트에서 실행하며 Supabase, Gemini API, OpenAI API만 원격 관리형 서비스를 사용한다. 클라우드 배포, 고가용성, 운영 autoscaling은 범위 밖이다.

```text
React/Vite
  |-- Supabase Auth 직접 호출: 가입·로그인·복구·비밀번호 변경
  |-- Authorization: Bearer <Supabase access token>
  v
FastAPI /api/v1
  |-- 인증·검증·소유권·제품 판정
  |-- SQLAlchemy/psycopg --> Supabase Postgres public schema + RLS
  |-- UploadFile stream --> Supabase Storage private buckets
  |-- pgmq.send ----------> Supabase Queues
  v
Python worker
  |-- pgmq.read/set_vt/delete/archive direct SQL
  |-- Gemini: 채팅·rolling summary·TTS·감정
  |-- OpenAI: 피드백·면접 분석·embedding
  `-- 결과를 기존 domain/job record에 멱등 갱신
```

## 3. 기술 스택과 채택 근거

버전은 잠금 파일을 진실 원본으로 두지 않는다. Front는 `package-lock.json`, Back은 `requirements*.txt`에 검증된 버전을 고정한다. 새 버전 반영은 공식 release/docs 확인, 로컬 품질 게이트, OpenAPI contract check 후 수행한다.

## 5. 계층과 판정 책임

```text
router(API) -> service -> repository -> SQLAlchemy/psycopg -> Supabase Postgres
                          \-> storage adapter -> Supabase Storage
service -> job publisher -> pgmq -> worker -> provider adapter
```

| 계층 | 책임 | 금지 |
| --- | --- | --- |
| Frontend 보조 계층 | Supabase Auth session 취득, Bearer 전송, route guard, 화면 상태·fallback 표현 | Client state를 권한 증거로 사용, owner·완료·허용 조합 최종 판정 |
| Auth dependency | Bearer 추출, JWT/JWKS 검증, `(session_id,sub)`의 `auth.sessions` 존재와 탈퇴 진행 상태 확인, canonical `authenticated_user_id` 생성, 민감 작업 `get_user` 재확인 | Body/query/path의 user ID 신뢰, domain resource 소유권 판정 |
| Router/API | route, Auth dependency 연결, Pydantic validation, HTTP status, idempotency header 수집 | 소유권 판정, 직접 owner-data query, AI 호출 |
| Service | 제품 규칙과 최종 판정, 상태 전이, transaction orchestration, repository 조합 | request body의 user ID 신뢰, owner-data 직접 SQLAlchemy query |
| Repository | owner predicate가 포함된 read/write/delete, lock·atomic update, persistence query | HTTP status·UI 판단, owner ID 생략 |
| Supabase/Postgres | `public` schema, constraints, transaction, RLS, pgmq/pgvector | RLS만 믿고 FastAPI Repository의 owner predicate를 생략 |
| Storage adapter | Server-generated object key, private bucket write/delete, owner 확인 후 signed URL 발급, 실패 정리 | 공개 URL 발급, client object key 신뢰, signed URL logging |
| Job publisher | Service가 확정한 owner/resource/version을 최소 job envelope로 만들고 domain 상태 저장과 enqueue를 조정 | Raw 문서·대화 원문을 queue/DLQ에 복제, 인증되지 않은 owner ID 수용 |
| Worker | lease, deadline/retry, provider adapter 호출, 전·후 stale check, 멱등 결과 저장 | 사용자 입력만으로 owner 결정, stale resource 결과 저장, raw payload logging |
| Provider adapter | Vendor 요청·응답을 공급자별 형식과 Pydantic domain result 사이에서 변환, timeout·safe error normalization | 제품 상태 전이·소유권 판정, raw provider payload 영구 저장 |

**서버 판정 예시:** Front가 `completed`, 점수, persona-scenario 허용, file 분석 가능, owner ID를 보내더라도 신뢰하지 않는다. Service가 인증 subject와 저장 상태를 기준으로 판정하고 Repository에 인증 user ID를 필수 전달한다.

### 5.1 Transaction 소유권

- Service가 유스케이스 transaction의 시작·commit·rollback 경계를 소유한다. 한 사용자 행동에 필요한 여러 Repository 호출, domain 상태 변경, idempotency 결과 확정의 원자성을 Service가 조정한다.
- Repository는 전달받은 Session 안에서 query·flush·lock·affected row 판정을 수행하되 독자적으로 commit하지 않는다. Repository가 commit하면 Service의 전체 유스케이스 rollback이 깨지므로 금지한다.
- Router, Auth dependency, Storage adapter, Provider adapter는 DB transaction을 소유하지 않는다.
- 외부 Provider·Storage network 호출을 DB transaction 안에서 장시간 유지하지 않는다. 먼저 서버가 허용 상태와 job/resource metadata를 transaction으로 확정하고, Worker가 외부 호출 전·후 별도 짧은 transaction에서 owner/resource/version을 재검증한다.
- DB 상태 확정과 pgmq enqueue 사이의 부분 실패는 Job publisher가 동일 idempotency key와 저장된 job 상태를 기준으로 재조정한다. 동일 요청이 새 domain resource나 중복 효과를 만들지 않아야 한다.
- 사용자 종료 Service는 소유권, 대화 유형, 현재 `in_progress` 상태를 검증하고 `completed`, `user_ended`, 종료 시각, 평가 대상 메시지 기준점, 단일 결과 레코드와 idempotency 결과를 하나의 transaction 경계에서 확정한다.
- 종료 결과 Job 발행 실패는 Job publisher의 재조정 대상으로 처리하며 이미 확정된 대화방을 `in_progress`로 되돌리지 않는다.

### 5.2 대화 종료 상태 전이와 일관성 경계

- 대화방은 `in_progress → completed` 전이만 허용하며 terminal 상태를 `in_progress`로 되돌리지 않는다.
- 종료 원인은 `goal_achieved`, `max_turns_reached`, `interview_completed`, `user_ended` 중 정확히 하나다.
- `user_ended`는 연습 유형과 무관하게 허용한다. 질문이 남은 면접이나 목표를 이루지 못한 시나리오도 사용자가 그만둘 수 있어야 하며, 그렇지 않으면 결과를 볼 방법이 없는 방이 남는다.
- 화면 이동, 브라우저 종료와 로그아웃은 대화방 상태 전이를 발생시키지 않는다.
- 종료 transaction은 조건부 atomic update 또는 row lock으로 메시지 처리 완료와 종료 요청의 경쟁을 직렬화한다.
- 종료 transaction이 획득한 시점까지 저장이 완료된 마지막 메시지 순번 또는 ID를 불변 평가 기준점으로 확정한다.
- 평가 기준점 이전의 저장된 사용자 발화는 표현 평가에 포함할 수 있지만 AI 응답까지 확정된 경우에만 완료 턴으로 계산한다.
- 사용자 종료 시 새로운 AI 종료 발화를 생성·저장하지 않고 UI 상태 안내만 사용한다. 목표 달성·최대 턴 도달의 사전 정의된 종료 발화는 기존 정책에 따라 사용할 수 있다.
- 종료 뒤 도착한 AI 응답·TTS·감정 분석·발화별 피드백은 저장 전에 room 상태와 평가 기준점 또는 version을 재검증하고 현재 대화에 연결하지 않는다.
- 발화가 없는 사용자 종료도 단일 결과 리소스를 생성하되 점수 없이 `평가 자료 부족`으로 표현한다.
- 자유채팅은 사용자·페르소나 조합당, 기본 상황 시나리오는 사용자·페르소나·시나리오 조합당 `in_progress` room 하나만 허용한다.
- `completed` room은 활성 유일성 대상에서 제외한다. 같은 조합의 재연습은 새 room을 만들고 기존 room·messages·result를 보존한다.
- 면접은 사용자·면접 구성 조합당 `in_progress` room 하나를 허용하고 완료 전 재진입은 기존 room을 반환한다.

## 6. 인증과 접근 제어

### 6.1 인증 흐름

- 가입·로그인·password recovery/reset/change는 React가 Supabase Auth에 직접 호출한다. FastAPI는 비밀번호를 받지 않는다.
- MVP는 email/password만 지원한다. OAuth/account linking은 범위 밖이다.
- 로컬 MVP는 email verification을 끄고 가입 직후 온보딩한다. 운영 전환 전 반드시 켠다.
- Supabase session은 `sessionStorage`에만 보존한다. 같은 탭 refresh는 복원하고 탭/브라우저 종료, logout, account deletion에서 제거한다.
- React는 FastAPI에 `Authorization: Bearer <access token>`을 보낸다.
- 일반 API와 polling은 JWKS cache 기반 로컬 JWT 검증 후 token의 `(session_id,sub)`가 `auth.sessions.(id,user_id)`에 존재하는지 확인한다. 허용 `alg`, `iss`, `aud`, `exp`, `session_id`를 검증한다.
- `kid` miss/key rotation 시 JWKS를 refresh하고 한 번만 재검증한다.
- 회원 탈퇴 등 민감 작업은 Supabase Auth `get_user`로 재확인한다.
- `account.delete` claim이 `in_progress`이면 일반 인증 API는 새 resource 생성을 막기 위해 `401`로 차단한다. 탈퇴 endpoint만 같은 active session으로 retry/reconcile할 수 있다. session DB를 확인할 수 없으면 fail-closed `503`이다.
- 인증과 데이터 소유권 검사는 별개다.

### 6.2 DBA 구현 기준

로컬 MVP의 현행 기준은 Supabase `public` schema와 RLS다. 비노출 `app` schema 이전과 migration/runtime DB role의 완전한 분리는 운영 전환 검토 항목이며, 로컬 시연을 위해 선행하지 않는다.

1. 현재 애플리케이션 테이블은 `public` schema에 유지하고 사용자 소유 테이블에는 RLS를 활성화한다.
2. RLS policy는 `auth.uid()`에서 시작해 직접 `user_id` 또는 검증된 parent ownership chain으로 행 접근을 제한한다. Catalog처럼 인증 사용자에게 공개되는 데이터는 읽기 범위를 명시한다.
3. Browser는 Supabase Auth에만 직접 접근한다. 애플리케이션 테이블 CRUD는 FastAPI를 통하며, publishable/anon key에 불필요한 쓰기 권한을 추가하지 않는다.
4. FastAPI와 worker의 direct Postgres session은 요청별 JWT context를 주입하지 않으므로, Repository의 owner predicate를 실질적 접근 통제로 유지한다. RLS는 Data API 직접 접근에 대한 defense-in-depth다.
5. 현재 스키마 변경 이력의 진실 원본은 `supabase/migrations/*.sql`이다. API 저장소에서 Alembic을 채택할 때는 기준 revision을 만든 뒤 소유권을 일괄 전환하며 동일 변경을 두 migration 체계에 중복 기록하지 않는다.
6. `pgmq`는 Data API/`pgmq_public`로 노출하지 않는다. Queue 생성·삭제와 worker 실행 권한은 서버 환경으로 제한한다.
7. Storage service role key는 API/worker server environment에만 둔다. Browser에는 publishable/anon key만 제공한다.

### 6.3 행 소유권 강제

- 인증 dependency가 JWT `sub`를 canonical `authenticated_user_id`로 만든다. Body/query/path의 사용자 ID는 owner 판정에 사용하지 않는다.
- 모든 사용자 소유 Repository method는 `authenticated_user_id`를 필수 positional/keyword 인자로 받는다.
- Read는 resource ID와 `owner_id = authenticated_user_id`를 같은 query predicate에 넣는다.
- Update/delete는 먼저 다른 사람의 row를 읽지 않고 resource ID와 owner predicate를 같은 atomic statement에 넣고 affected row count를 검사한다.
- 관계형 child 접근은 parent ownership을 join/exists predicate로 같은 query 안에서 검증한다. 예: message/TTS/feedback는 연결 room의 owner를 확인한다.
- 존재하지 않음과 다른 사용자 소유는 모두 동일한 `404` code/message/timing class로 응답해 resource enumeration을 막는다.
- Service/Router의 owner-data 직접 SQLAlchemy query는 lint/review 금지 항목이다. 공개 catalog/health처럼 owner가 없는 단순 조회만 예외다.
- Job polling도 job owner predicate를 적용하고 `result_resource`는 owner 검증 후에만 제공한다.
- Signed URL 발급 전 DB metadata owner와 object key prefix를 모두 확인한다. URL은 짧게 만료되고 로그에 남기지 않는다.
- 현재 direct Postgres runtime session에 사용자 JWT를 주입하지 않으므로 RLS가 FastAPI의 owner 검사를 대신한다고 간주하지 않는다. `public` 테이블의 RLS는 Data API 직접 접근을 제한하는 defense-in-depth이며 Repository owner predicate와 함께 유지한다.

#### 6.3.2 생성·목록·Worker·Storage 공통 규칙

- **생성:** Client가 `owner_id`, `user_id`, object key를 보내더라도 무시한다. Auth dependency의 `authenticated_user_id`만 새 owner로 사용한다. Persona-scenario 허용, room 상태, 자료 version과 backpressure는 Service가 판정한다. 생성과 action은 합의된 `Idempotency-Key` 범위에서 중복 효과를 막는다.
- **목록:** Owner predicate는 pagination cursor, filter, sort보다 먼저 빠지지 않는 필수 조건이다. Cursor를 복호화한 값으로 owner 범위를 바꿀 수 없고, count·next cursor도 인증 사용자의 결과 집합에서만 계산한다.
- **단건·변경·삭제:** Resource existence를 owner 조건 없이 먼저 조회하지 않는다. ID+owner 또는 parent owner chain을 한 query/atomic statement에 넣고 affected row count로 성공을 판정한다. 타인 소유와 없음은 같은 `404`다.
- **Worker:** Queue envelope의 owner/resource/version을 권한 증거로 신뢰하지 않는다. Provider 호출 전과 결과 저장 전 DB의 현재 owner·version·eligibility를 다시 확인한다. 삭제·교체·탈퇴 후 결과는 stale discard하고 연결하지 않는다.
- **Storage:** Bucket은 private이며 object key는 서버가 생성한다. Upload·replace·delete는 DB metadata owner/version과 object prefix를 함께 검증한다. Download/audio는 검증 뒤 짧은 signed URL만 반환하고 URL·원문을 log/queue/DLQ에 넣지 않는다.
- **오류 비노출:** `401`은 인증 실패, `404`는 없음/타인 소유, `409`는 소유권을 통과한 뒤의 제품 상태 충돌에만 사용한다. Owner mismatch에 `403`을 사용하지 않는다.

### 6.4 CORS·CSP·오류 노출

- `CORS_ALLOWED_ORIGINS`는 scheme+host+port 정확 allowlist이다. Wildcard와 광역 localhost regex를 금지한다.
- Method와 `Authorization`, `Content-Type`, `Idempotency-Key` 헤더만 실제 사용 범위로 허용한다.
- Dev CSP는 Vite HMR 최소 예외만, build/preview는 `default-src 'self'`와 승인된 FastAPI/Supabase 연결 및 필요한 image/media/style source만 허용한다. Inline script와 임의 origin을 금지한다.
- Supabase Auth 오류는 account enumeration을 피하는 안정적 client error code로 매핑해 i18n한다.

## 7. 데이터·파일 생명주기

- 사용자 자료와 TTS WAV는 Supabase Storage private bucket에 둔다. 공개 URL은 금지한다.
- 업로드는 FastAPI proxy 방식이다. `UploadFile` streaming, auth/owner, 확장자+magic bytes/actual MIME, 10MB 상한, server-generated object key를 적용한다.
- PDF/DOCX만 허용한다. DOCX macro·비정상 archive를 거부하고 파일을 실행하지 않으며 text extraction만 수행한다.
- ClamAV와 OCR은 MVP에 포함하지 않는다. Parsing time/memory/page limit을 적용하고 텍스트 추출 threshold 미달은 `DOCUMENT_TEXT_NOT_EXTRACTABLE`로 분석 queue 진입을 막는다.
- 저장 실패/metadata 확정 실패는 중간 object를 정리한다.
- 다운로드·재생은 owner 검증 후 짧은 signed URL로 제공한다.
- 자료 교체/삭제, room 삭제, account deletion은 PRD의 즉시 영구 삭제 범위를 따른다. Processing worker는 provider 호출 전과 저장 전에 resource owner/version을 다시 검사해 stale 결과를 버린다.
- 연습 종료는 room 삭제가 아니다. 종료된 room의 메시지, 발화별 피드백, TTS, 비공개 맥락 요약과 독립 결과는 사용자가 삭제하기 전까지 보존한다.
- 종료된 room은 owner 검증 후 room·message·feedback·audio 조회를 허용하지만 메시지 생성과 AI·TTS·감정·발화별 피드백 재시도는 차단한다.
- Room 삭제 후에도 독립 result snapshot은 `result.owner_id`를 기준으로 보존·조회한다. 원본 메시지 참조가 필요한 결과는 snapshot 또는 nullable reference를 사용해 삭제 생명주기와 분리한다.
- Application-level field encryption은 MVP에 추가하지 않는다. Supabase at-rest encryption, `public` schema RLS, 최소 권한, Repository owner predicate를 함께 사용하며 운영 위협 모델에서 재검토한다.

## 8. Queue와 Worker

### 8.1 Queue 분리와 처리

- `conversation_text`: 최우선. Gemini 대화 텍스트와 필요 시 rolling summary.
- `interactive_ai`: TTS와 감정 분석. 사용자가 응답을 기다리는 동안 처리되어야 하므로 지연에 민감하다.
- `evaluation_ai`: 발화 피드백, 세션 결과 생성, 시나리오 조기 목표 판정. 채점 성격이라 수 초~수십 초가 걸려도 대화 흐름을 막지 않는다.
- `document_analysis`: 문서 추출 후 embedding/면접 자료 분석과 면접 구성 생성.
- `interactive_ai`와 `evaluation_ai`를 나눈 이유는 우선순위다. 한 queue에 두면 60초짜리 결과 생성이 consumer를 점유해 TTS가 뒤로 밀린다.
- 각 queue는 `<queue>_dlq`를 가지며 필수 이름은 설정에서 정확히 검증한다.
- Queue는 durable/basic pgmq를 사용하고 unlogged queue는 사용하지 않는다.
- FastAPI는 auth/validation/save/enqueue 후 `202 Accepted + job_id`를 반환한다.
- React는 `GET /api/v1/jobs/{job_id}`를 2초 간격으로 polling하고 succeeded/failed/제품 최대 대기시간 도달 시 중단한다.
- Gemini 대화 텍스트 성공 후 TTS·감정·피드백을 fan-out한다.
- 목표 달성, 최대 턴 도달, 면접 완료와 사용자 종료는 동일한 `evaluation_ai` 세션 결과 생성 경로를 사용한다.
- 시나리오는 사용자 발화가 저장될 때마다 `scenario_goal_progress` Job을 발행해 필수 성공 조건 충족 여부를 판정한다. 제한 턴 전에 충족되면 방을 종료하지 않고 `ended_reason = 'goal_achieved'` 로만 표시해 사용자에게 종료 여부를 묻는다. 첫 턴이 오기 전에는 판정할 대화가 없으므로 발행하지 않는다.
- 결과 Worker는 종료 transaction에서 확정한 평가 메시지 기준점과 완료 턴 수만 입력으로 사용한다.
- Worker는 담당 base queue별로 `worker_heartbeats`를 upsert한다. Ready는 `REQUIRED_WORKER_QUEUES`에 지정된 각 필수 base queue에 `WORKER_HEARTBEAT_TTL_SECONDS` 이내 heartbeat가 있을 때만 성공한다. 필수 base queue 는 `conversation_text`, `interactive_ai`, `evaluation_ai`, `document_analysis` 네 개이며 코드의 `BASE_QUEUE_NAMES` 하나에서 파생한다. TTL에는 기본값을 두지 않는다.

### 8.2 Job 계약

공통 상태는 `queued`, `processing`, `succeeded`, `failed`, `cancelled`다. Job API에는 `type/status/progress/error/result_resource`만 제공하고 domain 결과는 성공 후 별도 조회한다.

- 전송 오류 429/5xx/timeout: 총 3회(최초 1+재시도 2), exponential backoff+jitter.
- `Retry-After`는 기능 deadline 안에서만 우선한다.
- 기능 deadline은 현행 runtime 정책 기준: 대화 텍스트 45초, 감정 15초, 피드백 30초, TTS 45초, 자료 분석 60초, 면접 구성 생성 180초, 세션 결과 생성 180초, 시나리오 목표 판정 60초다. 모든 유형은 최대 3회 시도하며 deadline이 다음 retry보다 우선한다.
- deadline 값은 코드(`app/services/jobs.py`)와 `processing_timeout_policies` 두 곳에 있다. 앞은 job 생성 시점의 deadline 을, 뒤는 reaper 가 거둔 job 을 재시도할 때의 새 deadline 을 정한다. 둘이 다르면 재시도가 다른 예산으로 돌므로 readiness 가 값까지 대조한다.
- Structured output Pydantic 검증 실패는 같은 job record에서 안전한 validation summary로 exactly one repair retry. 두 번째 실패는 final failed.
- Transport retry counter와 schema repair counter를 분리한다.
- Result write는 기존 단일 processing/domain record에 멱등 갱신한다.
- 세션 결과의 멱등 범위는 room attempt와 단일 result identity에 묶으며 하나의 room 시도에서 결과 레코드와 결과 Job을 각각 하나만 생성한다.
- 결과 생성이 실패하거나 일부만 성공해도 room의 `completed` 상태를 되돌리지 않고 같은 result record를 재시도한다.
- 사용자별 queued+processing 한도는 Postgres에서 atomic 판정한다. Provider별 worker concurrency는 환경변수이며 숫자는 부하 측정으로 정한다. 초과는 retryable `429`다.

### 8.3 Visibility·DLQ·취소

- Worker wrapper가 transaction과 visibility timeout을 명시한다. Visibility timeout은 가장 긴 180초 Job deadline보다 커야 하며, 설정 검증으로 이를 강제한다. 처리 중 별도 운영 작업으로 lease를 늘릴 때는 `set_vt`를 사용하고 중복 consumer에서도 job 상태 compare-and-set으로 단일 효과를 보장한다.
- 로컬 Worker entrypoint는 base queue별 `python -m worker.conversation_text`, `python -m worker.interactive_ai`, `python -m worker.evaluation_ai`, `python -m worker.document_analysis` 네 개다. 각 프로세스는 `WORKER_CONCURRENCY`만큼 consumer를 만들고 담당 Job 유형만 dispatch한다.
- Consumer thread 가 예외로 죽으면 프로세스를 즉시 종료한다. heartbeat 만 남기고 아무 Job 도 집지 않는 좀비 worker 는 readiness 를 통과하면서 queue 를 멈추므로, 조용히 사는 것보다 죽고 재시작되는 편이 낫다.
- 면접 결과 Worker는 고정 다섯 항목을 1~20 정수로 검증한다. 다섯 항목이 완전할 때만 합계 5~100을 저장하며 일부 누락은 `partial`, 전부 누락은 `failed`로 저장하고 채용 합격·불합격은 생성하지 않는다.
- 최종 실패는 queue별 `<queue>_dlq`로 안전 메타데이터(job_id/type/attempts/safe error/timestamps)만 원자적·멱등 이동한 뒤 source에서 제거한다.
- DLQ list/replay는 local admin CLI만 제공한다. Replay 전 job/resource/owner/version/현재 eligibility를 검사하고 새 idempotency key로 enqueue하며 안전 audit metadata를 남긴다.
- 범용 사용자 cancel API/UI는 없다. Delete/replace/account deletion이 queued job을 cancel하며 stale worker 결과를 저장하지 않는다.
- 연습 종료는 범용 Job cancel이 아니라 room의 domain action이다. 사용자 종료 cutoff 이후의 conversation/TTS/emotion/message-feedback 결과는 저장 전 room 상태와 기준점을 재검증해 `cancelled` 또는 stale discard하고 연결하지 않는다.
- 면접 room에는 임의 중간 종료 action을 노출하거나 허용하지 않는다. 다만 면접관 종료 발화로 `awaiting_user_end`가 확정된 뒤에는 기존 면접 완료 action을 제공하고, 사용자가 최종 확정하면 `completed + interview_completed`와 결과 Job을 한 transaction으로 저장한다.

## 9. AI와 RAG

### 9.1 Provider 경계

Provider SDK는 `app/ai/interfaces.py` 뒤에 둔다. Service는 vendor response를 직접 해석하지 않고 adapter가 Pydantic domain result로 변환한다.

환경변수:

```text
GEMINI_CHAT_MODEL
GEMINI_TTS_MODEL
GEMINI_EMOTION_MODEL
OPENAI_FEEDBACK_MODEL
OPENAI_INTERVIEW_MODEL
OPENAI_EMBEDDING_MODEL=text-embedding-3-large
OPENAI_EMBEDDING_DIMENSIONS=3072
```

모든 model ID는 시작 시 누락·API 허용 여부를 검사한다. `.env.example`에는 문서 검증일과 공식 링크가 있는 예시만 넣고 secret을 넣지 않는다. Preview TTS model은 고정 상수로 숨기지 않는다.

Provider-side 저장은 지원되는 옵션에서 끈다(OpenAI `store=false`). No-training/장기 보존 비활성 계정 설정을 startup checklist로 확인한다. 로컬에는 정규화된 메시지·피드백·source refs만 저장하고 raw request/response/reasoning/trace를 보존하지 않는다. 진단은 model, provider request ID, usage, safe error code만 남긴다.

### 9.2 대화 context

- 최근 메시지는 원문으로 유지한다.
- 측정된 token budget 이전에 오래된 span을 Gemini rolling structured summary로 만든다.
- Schema는 relation, situation, goals, agreements, unresolved, explicit important facts를 포함하고 inferred facts를 금지한다.
- Summary version과 last included message ID를 저장한다.
- 다음 입력은 summary+recent raw이며 trigger threshold는 공식 context limit과 대표 대화 측정으로 정한다.

### 9.3 RAG

```text
검증된 text PDF/DOCX
 -> local text extraction/normalization
 -> normalized text chunks (현행 250어절, 50어절 overlap)
 -> text-embedding-3-large 3072차원 embedding
 -> public.document_chunks + owner/document/analysis/version/source metadata
 -> owner/version metadata prefilter
 -> 자연어 검색 의도 문장으로 cosine similarity 최대 15개
 -> evaluation-derived threshold
 -> 근거가 될 수 있는지 LLM 재판정, unsupported 는 제외
 -> only passing evidence to GPT-5.6 Luna
 -> structured output + source refs
```

- Section/page/paragraph source refs를 보존한다.
- Threshold 숫자를 임의 설정하지 않고 대표 한국어 이력서 retrieval evaluation으로 도출한다.
- 검색어는 이력서 본문과 같은 문체의 서술문을 쓴다. JSON 을 그대로 임베딩하면 절반이 키
  이름과 기호이고, 질문 조건(언어·난이도)은 이력서에서 찾을 내용이 아니라 검색을 흐린다.
  긴 이력서 30개 측정에서 F1 이 0.394 에서 0.967 로 올랐다.
- 청크에 의미 섹션 라벨을 붙여 경험·리스크만 검색하는 방식을 시도했으나, 같은 조건에서
  재현율을 8%p 깎아 순손해였다. 채택하지 않는다.
- 근거 재판정은 "면접에서 파고들어 물을 경험이 있는가" 를 기준으로 한다. 질문 조건을
  기준으로 삼으면 대조할 대상이 없어 같은 입력에도 판정이 흔들린다.
- AI 에게 chunk_id·document_id 를 되돌려 받지 않는다. 후보에 1번부터 번호를 붙여 보내고
  그 번호로 판정과 질문 근거를 받은 뒤, 실제 ID 는 서버가 번호로 되찾아 채운다. 36자 UUID
  를 옮겨 적게 하면 없는 ID 를 지어내 job 이 통째로 실패한다. 측정에서 3% 가 그랬다.
- 재판정이 후보를 전부 버리면 등급을 임의로 올리지 않고 retryable 실패로 올려 기존 재시도
  정책에 맡긴다. 검색이 아무것도 찾지 못한 경우와 구분한다.
- 통과 chunk가 없으면 `insufficient_evidence`; 자료에 없는 사실을 만들지 않는다.
- Exact keyword miss가 반복될 때만 hybrid FTS를 재검토한다.
- 원본 교체는 새 document version을 re-embed하고 이전 활성 version을 배제한다. 삭제는 관련 chunks/vectors를 cascade 제거한다.

## 10. Front 상태·UX 경계

- TanStack Query: server state, cache key, retry, polling, invalidation.
- Zustand: UI language, TTS autoplay/mute, current playing message 등 client-only. Server state 복제 금지.
- `localStorage`에는 언어와 허용된 재생 환경설정만 저장한다. Auth는 `sessionStorage`다.
- 미전송 텍스트, 음성 전사, 프로필 수정값, 선택 파일은 세션 만료 시 보존하지 않는다.
- i18next 기본/fallback은 한국어이며 feature namespace를 사용한다. Server error `code`를 translation key로 매핑하고 dev missing key를 탐지한다.
- Web Speech API 음성 입력 공식 지원은 최신 Chrome/Edge desktop+Android다. Safari/Firefox/iOS 등은 즉시 text fallback을 제공한다.
- CSS Modules는 token만 사용한다. 색상·spacing·typography·radius·shadow 하드코딩은 금지하고 새 값은 디자인 시스템에 먼저 추가한다. 좁은 예외는 문서화하고 lint/check한다.
- Room 목록과 상세 cache는 서버가 반환한 `status`, `ended_reason`, `completed_at`을 진실 원본으로 사용한다.
- 사용자 종료 성공 후 room 목록·상세, result와 job query를 invalidate하고 다시 조회한다. 종료 실패 시 optimistic UI로 `completed`를 먼저 표시하지 않는다.
- 읽기 전용 여부는 별도 mutable server state로 저장하지 않고 `room.status == completed`에서 파생한다.
- `completed` room route는 기존 대화 화면을 읽기 전용으로 렌더링하고 입력·녹음·메시지 생성·AI 처리 재시도 action을 제공하지 않는다. 서버도 동일 변경 요청을 차단한다.

## 11. API 공통 계약

### 11.1 공통

- Base prefix: `/api/v1`
- JSON은 UTF-8. Upload만 multipart.
- 재시도 가능한 create/action API는 React가 생성한 UUID `Idempotency-Key` header가 필수다.
- Scope는 `user_id + route/action + key`; request fingerprint와 result를 저장한다.
- 같은 key+같은 payload는 기존 resource/job을 반환하고, 같은 key+다른 payload는 `409`다.
- 목록은 `(created_at,id)` stable order의 opaque cursor를 사용한다: `limit`, `next_cursor`. Resource별 asc/desc를 명시한다.

오류 envelope:

```json
{
  "error": {
    "code": "STABLE_MACHINE_CODE",
    "message": "safe default/developer message",
    "field_errors": [{"field": "name", "code": "INVALID_VALUE"}],
    "request_id": "uuid",
    "retryable": false
  }
}
```

FastAPI 전역 handler가 Pydantic validation, auth, domain, provider/queue 오류를 이 형식으로 통일한다. Client는 `code`를 i18n한다.

### 11.2 상태 코드 기준

| 코드 | 용도 |
| --- | --- |
| 200 | 조회·수정·기존 멱등 결과 |
| 201 | 동기 resource 생성 |
| 202 | 비동기 job 수락 |
| 204 | 응답 body 없는 삭제/로그아웃 후 정리 |
| 400 | 형식 외 잘못된 요청 |
| 401 | token 없음/만료/invalid |
| 403 | 인증됐으나 제품 상태상 금지; owner mismatch에는 사용하지 않음 |
| 404 | resource 없음 또는 다른 사용자 소유 |
| 409 | 상태 충돌, invalid persona-scenario, idempotency fingerprint 충돌 |
| 413 | 10MB 초과 |
| 415 | 지원하지 않는/MIME 불일치 파일 |
| 422 | field validation/document parsing 조건 실패 |
| 429 | user backpressure/provider 제한, retryable |
| 500 | 안전하게 변환된 내부 오류 |
| 503 | DB/queue readiness 실패 또는 일시 불가 |

## 12. API 명세 초안

DTO의 구체 필드명은 Pydantic/OpenAPI가 최종 기준이고, route·operationId·요청/응답·상태코드의 최종 계약은 `docs/API명세.md`다. 아래 표는 그 계약을 요약하며 DB schema를 의미하지 않는다. 두 문서가 다르면 구현자가 추정하지 않고 `docs/API명세.md`와 이 요약을 같은 변경 단위에서 정합화한다.

### 12.1 Health·profile·auth orchestration

| --- | --- | --- | --- | --- |

| `GET /api/v1/health/ready` | 없음 | 사용자 데이터 없는 local health 예외; 설정값 비노출 | 200 DB/extension/queue/config, worker heartbeat 또는 503 | 503 |

가입·로그인·recovery/reset/change/logout session 처리는 Supabase Auth SDK 직접 호출이므로 FastAPI `/auth/password` API를 만들지 않는다.

### 12.2 Catalog·rooms·messages

| Method/path | 요청 | 접근 제어·owner chain | 성공 응답 | 주요 오류 |
| --- | --- | --- | --- | --- |
| `GET /api/v1/personas` | cursor/limit/filter | Bearer; owner 없음, server active catalog만 | 200 items/next_cursor | 401 |
| `GET /api/v1/personas/{persona_id}` | path | Bearer; owner 없음, server allowed scenario 판정 | 200 detail+allowed scenarios | 401,404 |

| `POST /api/v1/messages/{message_id}/retry-response` | Idempotency-Key | `jwt.sub -> room.owner_id -> message`; retry 가능 상태 판정 | 202 existing response record + job ID | 401,404,409,429 |

`POST messages`는 room owner, active state, turn limit를 서버에서 판정한다. 동일 발화 retry는 새 user/AI message를 만들지 않는다.

사용자 종료 action은 같은 key의 중복 요청에는 기존 room/result/job을 반환한다. 서로 다른 key의 동시 요청도 조건부 상태 전이와 room attempt 단위 unique 결과로 단일 효과를 보장한다. 면접, 이미 종료된 room과 허용되지 않은 mode는 owner 확인 뒤 `409`다. `completed` room의 GET 조회는 허용하지만 message 생성과 처리 재시도는 `409`로 차단한다.

## 13. NFR와 품질 게이트

### 13.1 시간·복원력

- 확정 deadline: text 15s, emotion 15s, feedback 30s, TTS 45s, document analysis 60s, interview configuration 180s, session result 60s. 각 작업은 최대 3회 시도한다.
- Text 성공은 즉시 저장·표시하고 downstream 상태를 독립 저장한다.
- Retry는 같은 record를 갱신하고 중복 결과를 만들지 않는다.
- Offline/timeout/partial/empty/error는 현재 상태와 retry/fallback을 제공한다.
- 종료 상태 저장과 종합 결과 생성을 분리한다. 결과 실패·부분 성공에도 `completed` room은 유지하고 같은 result record만 재시도한다.

- WCAG 2.2 AA 목표, keyboard operation, visible focus, 4.5:1 text contrast, 3:1 large text/graphics, 44x44 touch, 200% zoom.
- 감정·점수·상태는 색만으로 전달하지 않는다. Audio에는 text, persona image에는 role/emotion alt를 제공한다.
- Reduced motion을 존중한다. Storybook a11y, RTL interaction, Playwright core E2E로 검증한다.

### 13.3 로깅·관측성

- JSON log 필드: request_id/job_id, safe internal user_id, route/job type, status, duration, provider error code.

- 종료 관측 로그에도 대화·문서 원문과 평가 prompt/result 원문을 남기지 않는다.

### 13.5 접근 제어 필수 테스트

다음은 architecture acceptance gate이며 정상 owner case와 다른 사용자·무인증 negative companion을 함께 둔다.

- **Auth 경계:** Token 없음·만료·잘못된 `alg/iss/aud/exp/session_id`, 폐기 또는 다른 사용자 session은 `401`; JWKS `kid` miss는 refresh 후 1회만 재검증; session DB 불가는 `503`; 민감 작업은 `get_user` 실패 시 중단한다.
- **Body owner 위조:** Create/update 요청에 다른 `user_id/owner_id/object key`를 넣어도 저장 owner는 JWT subject에서만 결정되거나 해당 입력을 거부한다.
- **단건 격리:** User B가 User A의 room, message, feedback, TTS, result, document, analysis, job ID를 요청하면 실제 미존재와 동일한 `404` envelope·code를 받는다.
- **목록 격리:** Room/message/result/document cursor 목록에 다른 사용자의 row가 한 건도 포함되지 않으며 `next_cursor`와 count 성격의 값도 owner 범위 밖 정보를 누설하지 않는다.
- **변경·삭제 원자성:** 타인 resource update/delete는 affected row 0과 동일 `404`이고, owner 없는 선조회나 존재 여부 차등 응답이 없다.
- **Parent chain:** Child ID를 알아도 parent room/document owner가 다르면 message·audio·feedback·analysis·session에 접근할 수 없다.
- **Job polling:** 다른 사용자의 `job_id`와 `result_resource`는 `404`; 성공 job도 domain resource owner가 일치하지 않으면 reference를 반환하지 않는다.
- **Idempotency 격리:** 같은 UUID를 서로 다른 사용자가 써도 scope가 분리된다. 같은 사용자·같은 route/action의 같은 key+다른 payload는 `409`이고 기존 결과를 바꾸지 않는다.
- **Worker stale check:** 호출 전 삭제, 호출 중 교체/version 증가, 탈퇴 후 늦은 응답 각각에서 결과가 저장·연결되지 않고 stale discard/cancel 상태가 된다.
- **Storage:** 타인 object metadata로 signed URL 발급·삭제·교체가 불가능하다. Public bucket/URL이 없고 signed URL·service role key가 log에 나타나지 않는다.
- **DB 권한:** `public` 사용자 소유 테이블에 RLS가 활성화되고 `anon`은 접근할 수 없으며 `authenticated` Data API 요청은 자신의 행 또는 명시된 catalog 읽기만 허용된다. Browser에 service role이나 direct DB 자격 증명을 전달하지 않는다.
- **Queue 권한:** Queue가 Data API에 노출되지 않고 Browser가 queue function을 실행할 수 없다. API/worker 서버 환경만 필요한 pgmq 동작을 수행하며 DLQ에는 raw conversation/document가 없다.
- **RLS 경계:** User B의 JWT로 Data API를 호출해 User A의 행을 읽거나 변경할 수 없어야 한다. 동시에 server direct query도 RLS에 의존하지 않고 Repository owner predicate로 같은 격리를 강제함을 확인한다.
- **오류 비노출:** 인증 실패는 `401`, 타인/없음은 동일 `404`, owner 통과 후 상태 충돌만 `409`; `403`으로 resource 존재를 누설하지 않는다.
- **종료 허용 범위:** 자유채팅·기본 상황 시나리오의 owner만 사용자 종료할 수 있고 면접·타인 room 종료는 각각 `409`·`404`다.
- **종료 원자성:** 메시지 처리와 종료가 경쟁해도 `completed`, 단일 ended reason, 평가 기준점과 완료 턴 수가 하나의 일관된 snapshot으로 확정된다.
- **종료 멱등성:** 같은 key와 서로 다른 key의 동시 종료 요청 모두 room 전이, result row와 result Job을 각각 하나만 만든다.
- **종료 후 stale 결과:** cutoff 뒤 완료된 AI·TTS·감정·발화 피드백이 종료 room에 연결되지 않는다.
- **읽기 전용:** `completed` room의 room/message/feedback/audio 조회는 owner에게 허용하고 message 생성과 모든 처리 재시도는 `409`로 차단한다.
- **재도전 보존:** 같은 조합의 새 연습은 새 room을 생성하고 기존 completed room·messages·result를 변경하거나 삭제하지 않는다.
- **결과 복원력:** 결과 생성 실패·부분 성공에도 room은 `completed`를 유지하며 같은 result만 재시도한다.

이 테스트가 하나라도 실패하면 unit/feature 성공 여부와 무관하게 contract/integration gate를 실패시킨다.

## 17. 아키텍처 완료 기준

- 모든 stack 항목에 채택 이유가 있다.
- Router/API, Service, Repository, Supabase 책임과 import/query 금지가 구분된다.
- 인증 subject와 owner predicate가 분리되고 모든 소유 resource에 같은 query-level owner 검사가 적용된다.
- 로컬 MVP의 `public` RLS, `anon/authenticated`, direct DB credential, Storage service role의 권한 경계와 운영 전환 재검토 항목이 구현 가능하게 명시된다.
- Queue, retry, deadline, polling, DLQ, stale-result 처리와 부분 성공이 PRD 시간 기준과 일치한다.
- API path, request/response 책임, 주요 status code, error envelope, idempotency, cursor 계약이 정의된다.
- 자유채팅·기본 상황 시나리오에서만 사용자 종료를 허용하고 면접 종료 요청은 UI와 서버 모두에서 차단한다.
- 모든 정상 종료는 `completed`와 정확히 하나의 `ended_reason`을 가지며 terminal 상태를 역전하지 않는다.
- 종료와 메시지 처리의 경쟁에서도 평가 기준점·완료 턴·단일 결과가 결정적으로 확정된다.
- 종료 이후 늦게 도착한 AI·TTS·감정·발화 피드백 결과는 종료 room에 연결되지 않는다.
- 종료된 room은 owner가 읽을 수 있지만 모든 변경 작업은 차단한다.

# 코딩 컨벤션

이 문서는 팀원이 읽기 쉽고 안전하며 유지보수하기 좋은 코드를 일관된 방식으로 작성하기 위한 공통 가이드입니다. 언어나 프레임워크별 공식 스타일 가이드가 있다면 이 문서와 함께 적용하며, 규칙이 충돌할 경우 프로젝트에서 합의한 설정을 우선합니다.

## 1. 기본 원칙

- 코드는 작성하는 시간보다 읽고 유지보수하는 시간이 더 길다는 점을 고려합니다.
- 동작하는 코드에 그치지 않고 의도가 명확한 코드를 작성합니다.
- 단순하고 명시적인 구현을 우선하며, 불필요한 추상화와 과도한 최적화를 피합니다.
- 중복을 줄이되, 서로 다른 개념을 억지로 하나의 추상화로 묶지 않습니다.
- 변경 범위를 작게 유지하고 기존 동작에 미치는 영향을 확인합니다.
- 팀에서 정한 Formatter, Linter, 정적 분석 도구의 설정을 따릅니다.
- 개인 취향보다 프로젝트 전체의 일관성을 우선합니다.

## 2. 이름 짓기

- 변수, 함수, 클래스 이름만으로 역할과 의도를 이해할 수 있게 작성합니다.
- 이름은 프로젝트 언어의 일반적인 명명 규칙을 따릅니다.
- 지나친 축약어와 한 글자 이름을 피합니다. 단, 반복문의 인덱스처럼 의미가 명확한 경우는 허용합니다.
- 함수는 동작을 나타내는 동사로, Boolean 값은 상태를 분명히 나타내도록 이름을 짓습니다.
- 컬렉션은 복수형을 사용하고 단위를 가진 값은 이름에 단위를 포함합니다.
- 같은 개념에는 같은 용어를 사용합니다. 예를 들어 한 객체를 코드마다 `user`, `member`, `account`로 혼용하지 않습니다.
- 의미가 불분명한 이름(`data`, `info`, `temp`, `value`, `result`)은 구체적인 이름으로 바꿉니다.

```text
# 권장
findUserById
isAuthenticated
activeUsers
timeoutMilliseconds

# 지양
getData
flag
list
tmp
```

## 3. 함수와 메서드

- 함수는 한 가지 일만 하며, 함수 이름으로 설명할 수 있는 하나의 추상화 수준을 유지합니다.
- 함수는 짧고 이해하기 쉽게 작성합니다. 길어지거나 여러 단계의 처리를 담당하면 의미 있는 단위로 분리합니다.
- 매개변수의 수를 최소화합니다. 관련 값이 많다면 의미 있는 객체로 묶는 것을 검토합니다.
- Boolean 매개변수로 함수의 동작을 크게 바꾸지 않습니다. 의도가 다른 동작은 별도 함수로 분리합니다.
- 입력값을 임의로 변경하지 않고 새로운 값을 반환하는 방식을 우선합니다.
- 함수 호출의 부수 효과를 예측할 수 있어야 합니다. 조회 함수가 데이터 저장이나 삭제를 함께 수행하지 않도록 합니다.
- 중첩을 줄이기 위해 검증 실패나 예외 상황은 조기에 반환하는 Guard Clause를 활용합니다.
- 사용하지 않는 매개변수와 반환값은 제거합니다.

```text
# 지양: 하나의 함수가 검증, 저장, 알림까지 모두 담당
registerUserAndSendEmailAndWriteLog(...)

# 권장: 책임을 분리
validateRegistration(...)
createUser(...)
sendWelcomeEmail(...)
```

## 4. 코드 구조와 책임 분리

- 클래스와 모듈은 하나의 명확한 책임을 갖도록 구성합니다.
- 비즈니스 로직, 입출력, 데이터 접근, 화면 표현 등 서로 다른 관심사를 분리합니다.
- 상위 수준의 정책이 데이터베이스, 외부 API 같은 구체적인 구현에 과도하게 의존하지 않도록 합니다.
- 공통 코드는 실제로 반복되고 변경 이유가 같을 때 추출합니다.
- 순환 의존성을 만들지 않습니다.
- 공개 API는 최소화하고 내부 구현은 외부에 불필요하게 노출하지 않습니다.
- 파일과 디렉터리는 기능 또는 도메인 기준으로 일관되게 구성합니다.
- 사용하지 않는 코드, 주석 처리된 코드, 불필요한 파일은 남겨 두지 않습니다. 필요한 이력은 Git에서 확인합니다.

## 5. 제어문과 가독성

- 조건문은 긍정적이고 이해하기 쉬운 형태로 작성합니다.
- 복잡한 조건식은 의도가 드러나는 변수나 함수로 분리합니다.
- 중첩된 조건문과 반복문은 가급적 2~3단계 이내로 유지합니다.
- 삼항 연산자는 단순한 값 선택에만 사용하고 중첩하지 않습니다.
- 언어가 제공하는 표준 컬렉션 처리 기능을 사용하되, 한 줄에 지나치게 많은 연산을 연결하지 않습니다.
- 숫자나 문자열 리터럴을 코드 곳곳에 직접 사용하지 않고 의미 있는 상수로 정의합니다.
- 경계값, 빈 값, `null`, 누락된 값의 처리 방식을 명시합니다.

```text
# 지양
if (user.age >= 19 && user.status == "ACTIVE" && !user.isBlocked) { ... }

# 권장
if (isEligibleUser(user)) { ... }
```

## 6. 오류와 예외 처리

- 오류를 삼키지 않습니다. 필요한 정보를 로그로 남기고 현재 계층에서 처리할 수 없다면 호출자에게 전달합니다.
- 빈 예외 처리 구문을 사용하지 않습니다.
- 모든 예외를 포괄적으로 잡기보다 처리 가능한 구체적인 예외를 구분합니다.
- 복구할 수 있는 오류만 현재 계층에서 처리합니다. 복구할 수 없다면 원인을 보존해 다시 던집니다.
- 예외를 다시 던질 때 원본 오류와 스택 트레이스를 유지합니다.
- 사용자에게는 이해 가능한 메시지를 제공하되 내부 구현, 스택 트레이스, 민감한 정보는 노출하지 않습니다.
- 정상적인 분기 처리를 위해 예외를 남용하지 않습니다.
- 리소스, 파일, 네트워크 연결, 트랜잭션은 성공 여부와 관계없이 안전하게 정리합니다.
- 외부 시스템 호출에는 타임아웃을 설정하고, 재시도는 멱등성·횟수 제한·지수 백오프를 고려해 적용합니다.

```text
# 지양
try:
    process()
except Exception:
    pass

# 권장 개념
try:
    process()
except ExpectedError as error:
    logger.error("처리 실패", error=error)
    raise ServiceError("요청을 처리하지 못했습니다") from error
```

## 7. 로깅

- 운영 중 문제의 원인과 흐름을 추적할 수 있도록 적절한 수준의 로그를 남깁니다.
- 로그 수준을 목적에 맞게 사용합니다.

| 수준 | 용도 |
| --- | --- |
| `DEBUG` | 개발 및 상세 진단 정보 |
| `INFO` | 정상적인 주요 처리 흐름과 상태 변화 |
| `WARN` | 처리는 가능하지만 확인이 필요한 비정상 상황 |
| `ERROR` | 요청 실패, 데이터 손상 가능성 등 즉시 확인할 오류 |

- 요청 ID, 사용자 식별용 내부 ID, 작업 종류 등 추적에 필요한 문맥을 구조화해 기록합니다.
- 비밀번호, 토큰, 세션, 인증 헤더, 주민등록번호, 결제 정보 등 민감한 값은 로그에 남기지 않습니다.
- 동일한 오류를 여러 계층에서 중복 기록하지 않습니다. 오류를 실제로 처리하거나 시스템 경계에서 전달하는 계층에서 기록합니다.
- 반복문 안의 과도한 로그와 정상 흐름의 불필요한 `ERROR` 로그를 피합니다.
- 문자열 연결보다 프로젝트의 구조화된 로깅 방식을 사용합니다.

## 8. 보안

- 비밀번호, API 키, 접근 토큰, 인증서, 데이터베이스 접속 정보 등 비밀값은 코드에 작성하지 않고 환경 변수 또는 승인된 비밀 관리 도구에서 읽습니다.
- `.env` 등 로컬 비밀 파일은 Git에 포함하지 않습니다. 필요한 키만 값 없이 `.env.example`에 문서화합니다.
- 모든 외부 입력은 신뢰하지 않으며 형식, 길이, 범위, 허용값을 검증합니다.
- 데이터베이스 쿼리는 매개변수 바인딩을 사용하고 문자열 결합으로 만들지 않습니다.
- 출력 위치에 맞는 인코딩과 이스케이프를 적용해 XSS 등 삽입 공격을 방지합니다.
- 인증과 권한 검사를 구분하고, 서버에서 모든 접근 권한을 검증합니다.
- 필요한 최소 권한만 부여하고 기본적으로 접근을 거부합니다.
- 검증된 암호화 라이브러리와 안전한 알고리즘을 사용하며 자체 암호화 방식을 만들지 않습니다.
- 의존성은 꼭 필요한 것만 추가하고 보안 취약점과 업데이트 상태를 정기적으로 확인합니다.
- 민감한 데이터는 저장과 전송 과정에서 보호하고, 불필요하게 수집하거나 오래 보관하지 않습니다.

## 9. 데이터와 상태 관리

- 데이터의 생성, 수정, 삭제 책임과 생명주기를 명확히 합니다.
- 공유되는 가변 상태를 최소화하고 가능한 경우 불변 데이터를 사용합니다.
- 여러 작업이 함께 성공하거나 실패해야 한다면 트랜잭션 경계를 명확히 설정합니다.
- 동시성으로 인한 중복 처리와 데이터 경합 가능성을 고려합니다.
- 시간과 날짜는 기준 시간대를 명확히 하고, 저장 시 UTC 사용을 우선합니다.
- 금액은 부동소수점 오차가 발생하지 않는 자료형으로 처리합니다.
- 외부 API나 저장소의 원본 데이터를 내부 모델에 직접 노출하지 않고 경계에서 변환합니다.
- 스키마 변경은 기존 데이터와 하위 호환성, 롤백 가능성을 함께 검토합니다.

## 10. 주석과 문서화

- 코드 자체가 무엇을 하는지 설명하도록 작성하고, 주석에는 코드만으로 알기 어려운 이유와 제약을 기록합니다.
- 코드와 불일치하거나 내용을 그대로 반복하는 주석은 작성하지 않습니다.
- 임시 해결책에는 배경, 제거 조건, 관련 이슈를 함께 남깁니다.
- `TODO`, `FIXME`에는 담당 맥락 또는 이슈 번호를 포함하고 방치하지 않습니다.
- 공개 API, 복잡한 알고리즘, 중요한 비즈니스 규칙에는 입력, 출력, 오류 조건을 문서화합니다.
- 설치 방법, 환경 변수, 실행·테스트·배포 절차가 바뀌면 관련 문서도 함께 수정합니다.

```text
# 지양: 코드를 그대로 설명
count += 1  # count에 1을 더한다

# 권장: 결정의 이유를 설명
# 외부 API의 호출 제한을 피하기 위해 결과를 5분간 캐시한다.
```

## 11. 테스트

- 새 기능에는 정상 동작을 검증하는 테스트를 추가합니다.
- 버그 수정에는 가능하면 해당 문제가 다시 발생하지 않도록 회귀 테스트를 먼저 추가합니다.
- 정상 사례뿐 아니라 경계값, 빈 값, 잘못된 입력, 오류 경로를 검증합니다.
- 테스트는 서로 독립적이어야 하며 실행 순서나 다른 테스트의 결과에 의존하지 않습니다.
- 테스트 이름은 조건, 동작, 기대 결과를 알 수 있게 작성합니다.
- 외부 API, 현재 시간, 난수 등 불안정한 요소는 제어 가능한 방식으로 대체합니다.
- 구현 세부 사항보다 외부에서 관찰 가능한 동작을 검증합니다.
- 테스트를 통과시키기 위해 운영 코드를 임의로 우회하거나 검증을 약화하지 않습니다.
- 테스트 커버리지는 품질을 확인하는 보조 지표로 사용하며 숫자 자체를 목표로 삼지 않습니다.

```text
# 권장하는 테스트 이름의 개념
유효한_사용자_정보가_주어지면_회원가입에_성공한다
중복된_이메일이면_회원가입을_거부한다
```

## 12. 성능과 외부 연동

- 측정 없이 성능을 추측해 복잡한 최적화를 하지 않습니다.
- 성능 문제가 확인되면 지표와 프로파일링 결과를 바탕으로 개선합니다.
- 반복문 안의 데이터베이스 조회와 같은 N+1 문제를 주의합니다.
- 대량 데이터는 페이지네이션, 스트리밍, 배치 처리를 고려합니다.
- 캐시는 만료 정책, 무효화 방식, 장애 시 동작을 함께 설계합니다.
- 외부 API 응답은 항상 성공하거나 예상한 형식이라고 가정하지 않습니다.
- 네트워크 요청에는 연결 및 응답 타임아웃을 설정합니다.
- 중복 요청이 발생해도 안전해야 하는 작업은 멱등성을 보장합니다.

## 13. 의존성과 설정 관리

- 새 라이브러리를 추가하기 전에 표준 기능이나 기존 의존성으로 해결 가능한지 확인합니다.
- 유지보수 상태, 라이선스, 보안 취약점, 번들 또는 실행 크기를 검토합니다.
- 의존성 버전은 프로젝트 정책에 맞게 고정하고 잠금 파일을 함께 관리합니다.
- 개발, 테스트, 운영 환경의 설정을 코드와 분리합니다.
- 환경 변수의 이름, 필수 여부, 기본값, 예시를 문서화합니다.
- 필수 설정이 누락되었거나 잘못된 경우 애플리케이션 시작 단계에서 명확한 오류를 발생시킵니다.
- 운영 환경에서 위험한 기본값이나 개발용 설정을 사용하지 않습니다.

## 14. 코드 리뷰 기준

리뷰어는 다음 사항을 우선 확인합니다.

- 요구사항을 정확히 충족하고 기존 기능을 깨뜨리지 않는가?
- 코드의 책임과 의도가 명확한가?
- 오류 처리, 보안, 동시성, 데이터 정합성 문제가 없는가?
- 테스트가 핵심 동작과 실패 경로를 충분히 검증하는가?
- 불필요한 복잡성, 중복, 의존성이 추가되지 않았는가?
- 로그와 문서가 변경 사항에 맞게 갱신되었는가?

리뷰 의견은 코드가 아니라 개선할 사항에 집중해 구체적으로 작성합니다. 작성자는 모든 의견을 확인하고 반영 여부와 이유를 답변합니다.

## 15. 작업 완료 체크리스트

- [ ] 함수와 모듈이 하나의 명확한 책임을 갖는가?
- [ ] 이름만으로 코드의 의도를 이해할 수 있는가?
- [ ] 중복, 불필요한 코드, 디버깅 코드가 제거되었는가?
- [ ] 오류를 삼키지 않고 적절히 처리하거나 전달하는가?
- [ ] 로그에 필요한 문맥이 있고 민감한 정보는 없는가?
- [ ] 비밀값과 환경별 설정이 코드에서 분리되었는가?
- [ ] 외부 입력을 검증하고 권한을 확인하는가?
- [ ] 정상·경계·오류 상황에 대한 테스트가 있는가?
- [ ] Formatter, Linter, 정적 분석, 테스트, 빌드가 통과하는가?
- [ ] 관련 문서와 설정 예제가 함께 갱신되었는가?
